# Executable domain contracts

The source of truth is `packages/contracts/src/index.ts`. These are strict Zod schemas shared by the API, local engine, workflow steps and UI. Objects reject unknown fields, UUIDs are validated, schema versions are explicit where defined, UTC timestamps use ISO `Z` values, time zones are validated IANA identifiers, and money uses safe integer minor units or null. Unsupported command types, malformed IDs and extra authority fields fail before execution.

The brief names 18 record contracts. The implementation also makes ContactRecord and Approval explicit: **20 documented records**, plus their nested schemas, separate status enums and the discriminated Command union. Examples are generated by executing the real domain fixture journey, then parsing every record with its public schema. They are not hand-written approximations.

- Full synthetic examples: [examples/contracts.v1.json](examples/contracts.v1.json).
- Rebuild examples: `pnpm exec tsx scripts/export-contract-examples.ts`.
- Validation test: `tests/contracts.test.ts`, “round-trips every documented contract example from a real fixture journey with strict schema versions”.

Examples use only `example.invalid` recipients and unmistakable `FIXTURE_ONLY_` receipts. They do not grant live permission or prove a real integration. Every example uses the same workspace, linked IDs and fixed fixture clock. Prior to any externally sourced import, convert the source into these schemas through its reviewed mapping; never let a source choose an actor, role, credential reference or approval.

## Separate statuses and units

OpportunityStage, ProposalStatus, RunStatus, ActionStatus, ApprovalStatus and InstallationStatus are independent enums. A proposal can be open while its follow-up is awaiting approval, a provider submission can be accepted while delivery is unknown, and an installation can be waiting for a reply while the scheduler is healthy. Unknown proposal status is never eligible. A newly encountered external status needs a reviewed mapping.

`Money` is a nonnegative safe integer or null, not a JavaScript floating-point currency amount. `500000` with `currency: "USD"` means USD 5,000.00. Zero is a recorded zero; null is unknown. `valueKind` distinguishes one-time, monthly recurring, total contract and unknown proposal values. Pipeline groups these units and currencies separately. Signed values with ambiguous/mixed value kinds remain unavailable. Paid-stage observations represent cumulative reconciled cash value, not the value of a contract or a second opportunity.

Stage counts are distinct per opportunity. A later `periodEnd` is the current snapshot; equally-current conflicting evidence yields unknown. A subsequent zero booking count can represent an explicitly sourced cancellation. Raw payments/refunds must be reconciled into a corrected cumulative paid snapshot before aggregation. The current schema does not model a general payment ledger; that is a deliberate extension boundary, not permission to add unlinked transaction rows together.

Human reply, booked, attended, signed, completed, invoiced and paid observations have independent evidence. A reply cannot imply a win, a Calendar event cannot imply attendance, and a payment cannot imply customer profit without fulfillment costs. `provider_verified`, `manually_reported`, `fixture` and `unknown` evidence qualities stay visible. Fixture observations cannot enter live metrics.

## Commands and checked mutations

The Command schema permits drafting, exact approve/reject, checked dispatch/reconciliation, fixture-only replies, explicit booking proposals, pause/takeover, goal recommendations/manual team selection, activation progress, bounded preparation, finding approval/initiative review, scenario saves, human time/cost records, CSV preview/import, manual outcome confirmations, briefs and fixture-only reset.

`record_outcome` requires an owner/assigned operator, a meaningful reference and observed UTC timestamp. Attendance/completion is a 0/1 count with null currency; signed/invoiced/paid is a cumulative safe minor-unit value with explicit currency. Reusing a reference with identical values is idempotent. A changed value needs a new correction reference/time and retains the original. Confirmation is manually reported outside fixture mode; it never masquerades as Google or payment-provider verification.

Boundary validation is necessary but not sufficient. Domain eligibility and the hosted SQL functions recheck current permission, source status, ownership, suppression, freshness, capacity and authority. Per-tenant SQL constraints and RLS remain the authoritative hosted isolation layer. The workflow's retained hook token is a server credential, not a public approval interface.

`AppSnapshot` is the UI read-model TypeScript interface, assembled from the executable record schemas. EngineState is the JSON-serializable local fixture service state, including private policy, claims, provider fixtures, source-version history and audit history. Only `snapshot(state)` is returned to the UI; private internals do not accompany it. Hosted state is reconstructed from authorized relational reads and must never fall back to fixture state.

## Version and extension rules

Keep v1 handlers available for in-flight v1 work; new definition versions affect new work and may not rewrite an approved message. Unknown schema versions fail, and a deployment transition must be verified on Vercel rather than inferred from fixture tests. API additions need matching runtime schemas, domain/SQL authorization and observable UI errors. Unsupported source mappings, model tool names, arbitrary SQL, arbitrary provider writes and client-controlled entitlement exceptions are outside these contracts.

Relevant test evidence is recorded in [TEST_EVIDENCE.md](TEST_EVIDENCE.md). Future source integrations should add explicit payment-ledger/correction linkage, status provenance and migration compatibility contracts where needed; missing semantics must remain a blocker rather than being guessed from text.
