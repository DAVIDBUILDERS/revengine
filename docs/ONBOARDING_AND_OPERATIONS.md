# Onboarding and operations

Current product: the local customer/operator console is usable with labeled fixtures. The hosted paths are implemented but need the actual projects, authorized sources, deployment and retained test evidence. Do not describe selected specialists, a connected OAuth account, an empty scheduler or a fixture receipt as a live working team.

## Responsibilities and first workflow

An owner chooses a goal and receives a five-slot recommendation from the 32-entry catalog. The recommendation explains applicability and shared prerequisites; choosing it does not make planned integrations work. Save the selection. Swapping a specialist with unfinished work requires a controlled handoff; historical artifacts, actions and ownership remain.

Capture the approved public company pages, review their evidence and explicitly confirm offers, customer types and operating context. Captured text is untrusted; models cannot promote it into authority. Use Connections to name each Google source/resource owner, exact Sheet file/range/column mapping, authorized sender and owned calendar. Resource checks are real read operations; the connection remains unconfigured until they pass. CSV is a validated bootstrap and never enrolls a person.

Assign an operator, provision capacity and reviewed policy using [PROVISIONING_RECORDS.md](PROVISIONING_RECORDS.md). Grant only the selected responsibilities. Configure model/provider and both model spending limits for generated preparation. Technical SEO's bounded snapshot checks do not require model inference. Shadow resume allows useful internal preparation with approved sources and capacity while outbound remains disabled.

The activation UI preserves progress, but its first-workflow milestone comes from saved artifacts/receipts/outcomes. Source-backed preparation, an authorized action receipt and an observed business outcome are distinct milestones. A wizard checkbox cannot create a verified provider result.

## Readiness dimensions

| Dimension | What it establishes | What it does not establish |
| --- | --- | --- |
| Integration | Current account grants, explicit resource mapping and retained read evidence | Permission to contact any person; verified send/calendar writes without receipts |
| Action | Current policy, selected capacity, source status, cohort, sender, ownership, staffed operator, deployment mode and approval/mandate | Guaranteed success; dispatch repeats every critical check |
| Measurement | Sufficient compatible evidence for a specific outcome/value definition | Profit or incrementality from a booking, signed proposal or manual payment alone |

Readiness is time-bounded. Stale source facts, expired/revoked tokens, changed columns, human takeover, opt-out, new reply, policy changes and expired approval invalidate affected work. Missing outbound permissions do not disable approved preparation. Missing model budget blocks model preparation without pretending a template or empty run is a successful model integration.

## Daily customer and operator routine

The customer opens Today for results, work underway, decisions and blockers. Sales records show the shared journey across specialists. Opportunity findings are business-work recommendations with hypotheses and source evidence; approving one creates an initiative with an owner, assignment, baseline, target and review date. It does not approve a send or a new commercial commitment. Retain inconclusive/failed reviews when evidence does not support success.

The assigned operator reviews component health and retained work, not only a provider status page. Check the last Cron tick separately from workflow, source, model, preparation and business evidence. Inspect dispatch backlog/dead letters, expired leases, blocked/failed runs, overdue decisions, stale reply coverage, submitting/uncertain actions and incomplete provider costs. Legacy Sites/Netlify remain unverified without independent probes; their timestamps cannot borrow successful work from Vercel.

Log setup, recurring support, provider, infrastructure and research work separately. Do not set an unknown cost to zero to improve margin. Review budget reservations and gateway billing evidence, then settle only supported amounts. Weekly briefs freeze the same SQL metrics as the dashboard; never rewrite numeric metrics with generated narrative.

## Exceptions

| Condition | Immediate behavior | Responsible next action |
| --- | --- | --- |
| Unknown/stale/closed proposal | Stop contact; invalidate stale review as needed | Source owner confirms dated authoritative status/version/scope |
| Any new reply | Stop the next follow-up; distinguish human, automatic, bounce, opt-out and ambiguity | Operator reviews original thread; positive intent can receive a structured appointment handoff |
| Suppression/opt-out | Persist suppression across workflows | Owner resolves only through a separate verified permission process; another agent cannot bypass it |
| Human takeover | Fence/cancel future automated contact | Named person owns the conversation until an explicit reviewed handoff |
| Workspace pause | Invalidate unsubmitted approvals and stop future dispatch | Reconcile already-submitting calls; resume performs readiness checks and creates fresh work, never revives old approvals |
| Provider timeout/uncertain result | Keep the reservation; do not resend | Read Sent Message-ID or exact Calendar event/attendee/time evidence; unresolved stays uncertain |
| OAuth revoked/expired | Stop affected reads/writes and dependent work | Account owner reauthorizes through a new one-time state; check actual scopes/resources again |
| Missing Sheet field/mapping drift | Reject ingestion/current action | Source owner repairs the explicit mapping and reviews material versions |
| Model error/invalid semantic output | No artifact/action; retain cost uncertainty | Review failure, source facts, budget and provider configuration; no blind same-run inference replay |
| Expired hook/decision or dead-letter dispatch | Visible blocked work | Operator traces run/outbox/approval IDs and recovers current state; never manufactures an approval |
| Over-capacity or ambiguous time | No booking | Coordinator asks a responsible person for a precise allowed time and reviews the same original conversation |

Pause cannot recall a provider request already accepted or in flight. Reconcile it before changing ownership or restarting a system. Booking notifications are outbound and require current authority. Booked status does not assert attendance, service delivery or revenue. Cancellation/rescheduling currently use an **assigned human handoff**: take ownership, pause affected chasing, verify the original event/person/purpose, perform the approved provider change, retain its evidence and record a separate correction. Automated provider cancellation/rescheduling is not implemented and must not be advertised as available.

## Source and outcome policy

The selected proposal system owns status, version, scope, amount, validity and contact identity. DAVID does not overwrite customer source columns in the pilot. Reimports preserve stable IDs; an omitted partial-export row is neither deleted nor won. The current Sheet batch is bounded to 500 data rows; larger datasets require reviewed partition/checkpoint work before enrollment.

Original Gmail thread metadata is required for a first follow-up. Mailbox-wide readonly scope is disclosed even though processing is restricted to enrolled conversations. A contact is never enrolled because it appeared in a Sheet or email. The release owner records a specifically permitted cohort and checks competing contact systems.

Manual attendance/signed/completed/invoiced/paid confirmations require a responsible person, date and reference and are labeled manually reported. Repeated same references are idempotent; changing historical evidence requires a linked correction/source reconciliation. No payment/refund provider adapter is currently connected. Do not create unlinked additive payment rows for refunds or cancellations; retain cumulative stage observations and their source references. Customer gross profit remains unavailable without fulfillment costs and collection evidence. Scenario value is a saved assumption, not an observed outcome or incrementality claim.

## Privacy, retention and files

Operational GET export is an authenticated, workspace-scoped **bounded screen snapshot**, not a complete privacy export. Use the separate administrative privacy CLI for full export/deletion once configured; its manifest and execution boundaries are documented with the script. Uploaded files use the private `david-evidence` bucket, workspace prefix, size/type restrictions and a `quarantine` path. Authenticated access and short-lived download links are enforced. There is no general antivirus/OCR pipeline or user-facing arbitrary-upload parser; quarantine files must not be promoted until an approved processor/reviewer validates them.

Proposed retention schedule for customer/legal review: website snapshots and quarantined imports 30 days, rejected temporary imports 7 days, operational conversation excerpts/artifacts 90 days, action/approval/outcome audit evidence 12 months subject to the customer's obligations. No schedule is claimed to be active automatically. A privacy request requires verified workspace authority, retention/legal-hold review, an export option, stopped/fenced work, credential revocation, object removal and audited tenant removal. Shared Auth identities must not be deleted merely because one workspace is removed. Backups require separate expiry/recovery handling; see the deployment runbook.

## Escalation and repeatability

Unattended live operation is blocked until an actual alert destination, delivery test, staffed hours and escalation owner are recorded. The UI and database heartbeat are implemented; they are not a delivered alert. During a staffed pilot, review exceptions at each operating interval and stop expansion if current status, reply coverage, ownership or uncertain writes cannot be explained.

Validate DAVID AI's first B2B proposal journey, then an external B2B customer with repeatable onboarding, then a deliberately different home-service process with its own proposal/job/payment sources and owner. Commerce remains catalog/scenario support until real integrations and evaluation exist. The conditional ten-working-day pilot target does not waive the hosted or legacy-replacement gates.
