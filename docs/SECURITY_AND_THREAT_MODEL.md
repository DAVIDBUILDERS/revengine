# Security boundaries and verification

DAVID's trusted authority is the intersection of verified user membership, environment restrictions, workspace policy, installation, approved cohort, current source state, conversation ownership and a current action approval/mandate. An email, spreadsheet, website or model response is evidence to evaluate, never an authority source.

## Identity and tenancy

Operational browser requests use Supabase Auth with the SSR cookie-refresh path and verified claims/current user verification at sensitive boundaries. Server authorization checks the selected workspace against current `memberships.actor_id`, role and `active`. DAVID operators require an explicit workspace assignment and MFA `aal2`. SQL enforces the same operator assurance so direct PostgREST requests cannot bypass application UI checks. Unknown/null roles deny access.

Exposed tenant tables have RLS and read-only browser grants. Tenant-aware foreign keys include `workspace_id`; knowing another workspace's UUID does not grant access or permit a cross-tenant reference. Browser credentials cannot directly forge an approval/receipt, grant an entitlement, change membership, enqueue private dispatch records or read Vault. Every public security-definer mutation fixes `search_path`, qualifies objects, checks current actor/membership and has explicit grants. The brief RPC discards submitted totals, evidence and narrative; it freezes database-derived observations. Direct product-record mutation cannot fabricate initiatives or verified activation milestones.

Background SQL uses separate restricted worker/dispatcher/OAuth logins, never a service-role/admin fallback. The worker does not own tables or bypass RLS. A dispatcher routing capability binds a persisted run to protected context keyed by transaction ID/backend PID. A caller-supplied workspace setting is insufficient. Each request/step ends its transaction before releasing the pooled connection. The dispatcher has narrow scheduling metadata access, without customer message or token access. The OAuth broker can finalize a valid consumed state but cannot enumerate Vault.

## Credentials and external actions

Customer Google integration authorization is separate from DAVID login. OAuth state binds actor, workspace, exact allowlisted HTTPS redirect, expiration and PKCE verifier. State hashes are one-time; replay/wrong-actor/wrong-redirect requests fail. The callback verifies Google UserInfo subject and verified email before the restricted broker stores connection tokens. Capability health is initially unconfigured, not automatically verified by a successful OAuth redirect.

Vault references are connection-bound. Read access checks the worker's current run/connection and permitted operation. Refresh uses a persisted lease and atomic token replacement, retaining a rotated refresh token. Disconnect deletes the stored token, empties capabilities, marks revoked and stops affected work; provider-side access removal remains an explicit account-owner verification step. Never place tokens, refresh verifiers, hook tokens, database URLs, credential-bearing errors or full message bodies in workflow inputs/outputs, browser state, audit detail or logs.

Only the shared action service imports raw provider writes. Dependency checks enforce this boundary with an explicit connector-test exception. The action service validates the immutable payload hash and source snapshot, refreshes the exact approved Sheet/thread before reservation and again before submitting, and rechecks SQL authorization immediately before the write. A source edit without a version increment still invalidates the approval: recipient, owner, scope, validity, currency, amount, value kind, issue date and version are compared with the saved snapshot. Missing/duplicate columns, unknown status and ambiguous source identity are blockers.

The persisted `submitting` transition defines in-flight work. Pause prevents subsequent transitions; a provider call already in flight may complete and must remain visible/reconciled. Shared contact ownership, explicit positive-reply scheduling handoff and fencing prevent independent specialists from claiming the same permitted action. Booking ends appointment chasing; no routine labels a promotion as a service message to avoid suppression.

Gmail sends have no application-wide exactly-once guarantee. The adapter makes one write attempt with a stable RFC Message-ID. Network/5xx/invalid-2xx receipt failures become uncertain, retaining ownership and reservation. Reconciliation checks Sent identity without resending; missing evidence is not permission to retry. Calendar inserts use stable allowed event IDs and immediate free/busy checks. Existing-event reconciliation verifies the action metadata, attendee and times on the approved calendar. Provider acceptance, recipient delivery, booking, attendance and financial stages remain distinct.

## Untrusted input, uploads and public URLs

All shared API/model/command shapes use runtime schemas. Model output cannot select secret references, tenant IDs, SQL, recipients outside approval, tools, new permissions or pricing commitments. Render text safely; do not execute HTML, Markdown scripts or imported code. Schema-valid text still needs factual/semantic validation. A prompt injection is retained as untrusted input and cannot broaden the action-service authority.

Website capture allows HTTPS public DNS hostnames on port 443 only. It rejects credentials, IP literals and internal/local names; checks every DNS answer against private/reserved ranges including IPv4-mapped IPv6; pins the approved DNS answer into the HTTPS request while preserving certificate hostname verification; and repeats validation on redirects. Limits: at most three redirects per page, three captured pages, same-origin discovered links, 512 KB/page hard ceiling, 1 MB total hard ceiling, 20-second crawl budget plus bounded in-flight fetch/DNS timeout, and no scripts/forms. Compressed unexpected responses and unsupported content types fail. Captures expose coverage and require confirmation of important facts. The public demo additionally needs the application's session/global quota gates before enabling URL processing.

Evidence is in a private Supabase bucket. Membership is checked as well as path prefix. Uploads are confined to `<workspace>/quarantine/...`, file size/type limits and authorization; application parsing must inspect actual content. Evidence downloads first authorize the record and return short-lived links with private/no-store response caching. A database backup alone does not back up Storage object bytes.

The anonymous sales demo is a separate Vercel project/session-local fixture experience. It must have no operational Supabase, Google, Cron, workflow-resume or AI credentials. Fixture identity is local/test only. Preview/development credentials must be isolated from production, with independent live-execution flags and explicit expected project IDs. Wrong-project migrations/seeds fail before changing data.

## Durable events and records

Approval, audit and outbox changes commit together. Hook registration recovers decisions already saved. Inbox keys reject repeat provider events; outbox leases and run ownership handle overlap/uncertain starts. The Gmail poll saves processed replies and cursor together with optimistic cursor comparison. Reconciliation reads only enrolled threads and records baseline/offset; an enrollment-list change during a partial rescan is an explicit restart/review condition. Earlier history must not overwrite the latest reply classification. Realtime is only a read notification channel; refetch and stored due work determine correctness.

Audit events and receipts are append-only to runtime/browser callers. Corrections are new records. Retain only the enrolled business conversations, bounded excerpts and evidence references required for the workflow. Default proposed retention until an accountable owner approves a policy: OAuth verifier until completion/expiry cleanup, synthetic public-demo state until session reset, website snapshots 30 days, operational messages/evidence 90 days, approved business/audit/outcome history 365 days. These are implementation-planning defaults, not a legal retention claim; legal holds, contractual obligations and user deletion rights require owner-confirmed policy before live enrollment. No automated destructive retention job is enabled without that approved policy.

Authorized export/deletion must verify current ownership, include linked records/objects, preserve required correction history, revoke source access and follow the selected retention policy. Cross-tenant export is forbidden. Restore testing must cover relational rows, Storage bytes, Auth settings/users, Vault decryptability, OAuth client configuration and custom-role credential rotation together. RPO/RTO and backup/PITR features depend on the purchased plan and must be tested on an authorized nonproduction project. Restoring code alone cannot retract submitted provider actions.

## Verification status and residual gates

Local deterministic tests pass for Google request boundaries, stable send identity/uncertainty, Calendar availability and identity, OAuth request/PKCE construction, SSRF DNS/redirect/IP blocking, exact approved resource selection, reply chronology and material source-field changes. These tests use labeled synthetic HTTP/DNS fixtures. They do not prove a hosted project's configuration or real Google consent/operation behavior.

The authored hosted SQL suites exercise actual authenticated/worker/dispatcher/OAuth roles, two tenants, tenant-aware FKs, operator MFA, denied browser mutations, denied Vault enumeration, forged routing context, reused-connection isolation, one-time OAuth state, atomic/repeated approval and hook registration, action fences and budget settlement. Running them is blocked by missing authorized nonproduction credentials. Separate-connection concurrency/load, real Storage signed download authorization, Google consent/revocation, Vercel wait/resume/deployment transition, MFA setup, real alert delivery and full restore rehearsal remain mandatory hosted gates. A green local suite is not a claim that those gates passed.

Threats requiring continued operational controls include compromised trusted deployment code, stolen runtime credentials, inaccurate owner-confirmed source facts, unseen communication from other mailboxes/tools, provider indexing delay, unconnected calendar conflicts, and unavailable historical deployments. Limit production secret/deploy access, require reviewed cohort boundaries, reconcile uncertain effects and configure accountable alert coverage before unattended live use.
