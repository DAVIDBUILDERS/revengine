# Development without Docker

Use Node 24.21.0 and pnpm 10.33.2. No command in this project needs Docker, a local Supabase service, an AWS account or a container database. The working branch is `codex/david-engine-v3`. Package versions and lockfile are committed with the implementation; upgrade deliberately and repeat the affected verification.

## Offline product

```sh
pnpm install --frozen-lockfile
pnpm fixture
```

Open http://localhost:3000. No `.env` file is needed. The local UI runs the real domain command handlers against explicit synthetic providers and an opaque per-browser file repository. Files live under `apps/web/.fixture` by default; they are ignored by Git. Use Reset in the UI to clear only the selected synthetic session. Never put production data in this directory. Selecting the second illustrative workspace exercises separate state; it does not prove hosted RLS.

`pnpm demo` starts the independent public-demo code at http://localhost:3001. Its data remains in that tab's sessionStorage. It has no operational cookies, database queries, OAuth, model calls or outbound actions. Website analysis is an explicit preset fallback. It is safe to demonstrate its planning interface without suggesting that a real company was analyzed.

```sh
pnpm lint
pnpm typecheck
pnpm test
pnpm exec playwright install chromium
pnpm test:e2e
pnpm build
```

Playwright starts and stops the two Next development servers. Stop an unrelated server on the same ports before running it. Screenshots and traces are local artifacts under `test-results`/`playwright-report`. Production builds validate both apps and Workflow bundling; they do not invoke a real cloud Workflow. The Workflow SDK's local development endpoints are generated by `withWorkflow`; fixture commands intentionally use the local domain service, so fixture success is not a durable-wait test.

## Hosted integrated development

Create an authorized managed Supabase **test** project distinct from production, and a dedicated Vercel test project. Put test runtime settings from `.env.example` in `apps/web/.env.local` for local shadow development. Configure server-only variables in the intended Vercel environment when deploying. Use `DAVID_MODE=shadow`, `DAVID_DEPLOYMENT=test`, `DAVID_LIVE_EXECUTION=false`. Never inherit a production secret into a preview.

Administrative tools load `.env.tools.local` from the repository root. Keep it untracked and out of the web runtime. Required fields are listed in `.env.tools.example`. Never print its contents or paste credentials into an issue. The migration tool uses a verified direct/session connection; the application uses restricted transaction-pooler logins with `prepare:false`, a small pool, and verified TLS. A provider-owned pooler hostname is not an application dependency on the provider's underlying infrastructure.

```sh
pnpm db:preview
pnpm db:apply
pnpm test:db
pnpm test:db:concurrency
pnpm db:seed
pnpm db:types
pnpm run doctor --remote
pnpm dispatch:tick
```

Every command above requires its documented external target. `db:preview` checks the actual migration ledger without schema writes or a shadow database. `db:apply` verifies project binding, serializes with an advisory lock and commits each migration with its checksum. Do not edit a migration after applying it. The migrations in this initial branch have **not** been applied to any project.

`test:db` executes transaction-wrapped SQL against the hosted test database, using actual `authenticated`, worker, dispatcher and OAuth roles within each suite. It requires a setup-capable test database login; it cannot be pointed at the declared production project. Hosted cases roll back their synthetic records. Multi-session contention and actual HTTP/Storage/Auth tests are separate release gates. Missing access exits BLOCKED, not PASS.

`db:seed` requires two existing test Auth user IDs and creates paused, non-enrolled, explicitly synthetic workspaces. It neither creates users nor sends invitations. `db:types` introspects the actual hosted schema; current checked-in types are a reviewed declaration, not a claimed hosted generation result. Review generated diffs before commit.

Use **`pnpm run doctor`**, not `pnpm doctor` (pnpm has its own built-in doctor). Local doctor checks configuration and names missing capabilities. `--remote` additionally reads the explicitly named Vercel project and restricted database role attributes when credentials exist. It does not turn configuration presence into an integration pass.

## Environments and promotion

| Target | Data/credentials | Outbound |
| --- | --- | --- |
| Local fixture | Synthetic only; credentials rejected | Fixture adapter only |
| Public demo | Independent synthetic sessions; operational secrets rejected | None |
| Local shadow / Vercel test / preview | Authorized nonproduction project and separately granted sources | Disabled |
| Operational production | Explicit matching production project, approved real source accounts | Disabled until both environment flag and current workspace activation permit it |

Automatic Cron runs against a Vercel project's production deployment. Test it using the dedicated **test project's production deployment**, still configured as shadow/test. Preview-only success does not establish scheduling. The current five-minute cron requires a supported paid plan. Read [DEPLOYMENT_RUNBOOK.md](DEPLOYMENT_RUNBOOK.md) before provisioning or promotion.

## Independent database sessions

`pnpm test:db:concurrency` additionally requires `TEST_WORKER_DATABASE_URL` and `TEST_DISPATCHER_DATABASE_URL` for the actual restricted roles in the same test project. It opens separate transactions and proves distinct backend IDs before simultaneous approval, action reservation and final-submission checks. Its random, marked fixture is committed so both sessions can see it; no provider call is made, due work is disabled/deferred, and cleanup is equality-bound to only those UUIDs. If cleanup fails, it attempts to pause the test workspace and prints exact recovery IDs. Review them before cleanup; never run a broad table deletion. Do not use this harness against production. Global dispatcher/model concurrency and hosted Workflow/provider behavior are separate tests.
